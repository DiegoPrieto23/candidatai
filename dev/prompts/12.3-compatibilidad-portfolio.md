# Fase 12.3 · Demo y portfolio: matriz de compatibilidad, README y seguridad

Última de las tres subfases de `dev/prompts/12-demo-portfolio.md` (12.1 → 12.2 → 12.3), en la rama
`fase/12-demo-portfolio`, con un commit por subfase. Cierra la fase 12.

## Contexto
Lee `dev/prompts/12-demo-portfolio.md`, `docs/AGENTS_COMPAT.md`, `docs/ARCHITECTURE.md`,
`dev/DECISIONS.md`, `docs/POLICIES.md` §5 y §6, `dev/RESUMEN_FASES.md` y `evals/REPORT.md`.

## Objetivo
Que la compatibilidad con agentes esté probada y documentada, que el README cuente bien el
proyecto y que el repositorio sea seguro de publicar.

## Alcance
1. **Matriz de compatibilidad probada.** Con el modo demo (`JH_DATA_DIR=data-demo`) y las mismas
   5 ofertas (fijadas en `evals/compat/jobs.txt`), ejecuta `procesar-ofertas`, `evaluar-encaje` y
   `generar-cv` en:
   - Claude Code con MCP (sesión arrancada con `JH_DATA_DIR=data-demo`);
   - Claude Code sin MCP (solo comandos `jh … --json`);
   - Codex, y cualquier otro agente disponible. El usuario los instala y los ejecuta siguiendo
     una guía (`dev/pruebas/fase-12-compatibilidad.txt`); el agente prepara la guía y la tabla.

   Para cada uno, en `docs/AGENTS_COMPAT.md`: qué funcionó, qué hubo que ajustar en
   `.agents/manifest.yaml` (y regenerar), tiempo y permisos pedidos, y los resultados de
   `jh eval cv` por agente. Lo no probado se marca así, sin suponer.
2. **README principal de portfolio** (sustituye la presentación de «kit de arranque»):
   - problema y qué hace la app;
   - arquitectura con diagramas Mermaid (capas, flujo de una oferta por etapas, agente ↔
     MCP/CLI ↔ servicios);
   - decisiones clave con enlace a sus ADR;
   - capturas de la UI demo (`docs/img/`, hechas con Playwright sobre `data-demo/`);
   - métricas de los evals (enlace a `evals/REPORT.md`);
   - cómo arrancarlo (con la demo en menos de 5 minutos);
   - límites éticos (POLICIES §5 y §6);
   - agentes compatibles y cómo añadir uno;
   - crédito al proyecto original.

   La guía para desarrollar por fases pasa a `docs/` o a una sección final.
3. **Revisión de seguridad:**
   - grep de datos personales (nombre, correo, teléfono, ciudad, empresas del perfil real,
     rutas de `data/`) en todo el historial (`git log -p --all`);
   - comprobar que `data/`, `data-demo/` y `.env` nunca se han commiteado;
   - revisar las capturas y los ficheros de `dev/pruebas/`.

   Si aparece algo, se para y se pregunta al usuario antes de reescribir el historial. Resultado
   en el registro.
4. **CI:** un paso que ejecuta `jh demo seed` en una carpeta temporal como prueba de humo.

## Decisiones tomadas al implementar
- Codex no se usa en esta fase (decisión del usuario): su columna queda «sin probar».
- Las 5 ofertas de la matriz son casos de `evals/cv/cases.jsonl` (`jh demo seed --compat`), para
  medir con la misma URL la extracción y el CV.

## Criterios de aceptación
- Clon limpio + `jh demo seed` + `jh serve` + `pnpm dev` muestra la app llena en menos de 5
  minutos (cronometrado, con los pasos del README).
- CI en verde.
- `docs/AGENTS_COMPAT.md` con la matriz rellena (o marcada «sin probar» con motivo).
- Revisión de seguridad sin hallazgos o con los hallazgos resueltos con el usuario.

## Al terminar
Actualiza `dev/ROADMAP.md` (filas 12.3 y 12, y registro), `dev/RESUMEN_FASES.md` y propón al
usuario un texto corto para LinkedIn o el CV que describa el proyecto con datos reales (número
de tests, métricas del eval, agentes probados), sin exagerar.
